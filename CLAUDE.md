# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Shrimp-5 is a Pokemon-inspired turn-based battle game in Unity 6000.3.9f1 (URP 2D). It started as
a game jam project, so expect rushed code outside the areas listed below. Controls and presentation
are Undertale-like: fixed 4:3, Z/X/C/arrows/ESC, keyboard only.

## Ownership boundary (read this first)

The repo has two owners. **Andy owns the UI; Owen owns the game logic.**

- **Only edit scripts under `Assets/Scripts/UI/`.** That is the entire editable surface by default.
- `Assets/Scripts/BattleUIContract.cs` (namespace `Sh.UIContract`) is the API between the two
  halves. **Read it as reference, don't edit it.**
- `Assets/Scripts/UIAndLogicCommunicator/` is Owen's game logic despite the folder name. Don't
  edit it. If you find bugs there (you will), report them rather than fixing them.
- `Assets/Scripts/Utility/`, `Player/`, `ScriptableObjects/` are shared — ask before editing.

Andy is fine with restructuring his *own* existing UI scripts when it's better practice, not just
appending to them.

## Authorship headers

Every script carries a `// written by ...` comment near the top. **Add yourself to it on anything
you author or edit.** New file → `// written by Claude Opus 5`. Editing someone else's → keep
their line and add one below naming what you changed (`// restructured into a panel coordinator
by Claude Opus 5`). Existing headers already credit tools this way (`// generated by Google
Gemini 3 Pro, checked by andy`), so AI authorship is expected to be stated, not hidden.

## Commands

**There is no test suite** (the test-framework package is present but there are no test assemblies
or test files) and **no asmdefs** — every script compiles into `Assembly-CSharp`.

The only way to verify a change without opening the Unity editor is to compile against Unity's
assemblies:

```bash
python Tools/compilecheck.py
```

Exits non-zero on any compile error, so it works as a gate. It builds a throwaway copy of
Unity's generated `Assembly-CSharp.csproj` with the file list corrected, then deletes it —
necessary because Unity only regenerates that project when the editor has focus, so its
explicit `<Compile Include>` list misses scripts you just added (phantom "type not found"
errors on your own new code) and still lists ones you just deleted (CS2001).

**As of 2026-10-16 compilecheck is broken:** `dotnet build` fails with `MSB3107` on the
`Assembly-CSharp-firstpass.csproj` project reference before compiling anything. It's in
`Tools/`, so ask before fixing it. Until then, use the live editor's compiler (below).

### Driving the editor (Unity CLI)

The project has the `com.unity.pipeline` package, so when Andy has Unity open the `unity` CLI
(`/opt/homebrew/bin/unity`) can drive the live editor: edit scenes and prefabs, compile, enter
play mode, run C#, and capture the game view. Check `unity status` first. **Prefer this over
hand-editing `.unity`/`.prefab` YAML** whenever the editor is reachable. Things that bit last time:

- Pass `--caller plugin --skill unity-cli` on every `unity command`.
- `eval`/`eval_file` wrap your code in a method body, so `using` directives don't compile. For
  anything big, use `run_script` with a `public static class` and a static entry method; the
  file can live in the scratchpad. Use `--dry_run true` first to get compile diagnostics.
- After editing `.cs` files, call `AssetDatabase.Refresh()` through eval, then poll
  `recompile_status`. `recompile` alone says "up_to_date" because the editor hasn't noticed
  the files changed.
- `editor_play` sent during a domain reload is silently dropped, and `eval` then runs against
  the **edit-mode** scene and can dirty it. Poll `Application.isPlaying` before poking anything.
- Play mode barely ticks while Unity isn't the focused window. `Application.runInBackground =
  true` fixes that, **but in the editor it writes `PlayerSettings.runInBackground` and gets
  saved into `ProjectSettings.asset`**. The same goes for `Time.timeScale` → `TimeManager.asset`.
  Put both back afterwards (`PlayerSettings.runInBackground = false`, `Time.timeScale = 1`) and
  check `git status` for stray `ProjectSettings/` changes. Playing also grows the dynamic TMP
  font's atlas (`Assets/Fonts/*.asset`); `git checkout` that if you didn't mean to change it.
- `capture_game_view --save_path` resolves relative to `Assets/` and refuses paths outside the
  project, so it creates real assets. Copy the screenshot out and `AssetDatabase.DeleteAsset`
  the folder afterwards.

Scene wiring and play mode are verifiable this way. Still say plainly what you did *not*
check (feel, animation, anything only visible when you actually play).

## Architecture

### The contract boundary

`BattleUIContract.cs` defines the whole UI↔logic API:

- `BattleEvent` — one "god struct" with 15 `BattleEventType` values. Logic pushes these to the UI.
- `IBattleUI` — `InitializeBattle(BattleSetupData)` + `QueueEvent(BattleEvent)`.
- `IBattleCommands` — `SelectAction(string actionID, ActionType)` is how the UI tells logic what
  the player chose. `ActionType.Attacking` takes a `moveID`, `Switching` takes a shrimp `instanceID`.
- `IBattleEventHandler` — `CanHandle` / `ForceSkip` / `IEnumerator HandleEvent`.

**Logic is synchronous and never waits for the UI.** `TurnManager.RunTurn` resolves an entire turn
in one frame and fire-and-forgets ~10 events into the UI's queue; the UI drains them over the
following frames. That's why `BattleEvent` carries both `deltaValue` and `finalValue` — always
drive bars and numbers from `finalValue` so the UI can't desync. It's also why anything reachable
from `UIShrimpState` that is a *live reference* into logic state (notably `statusEffects`) is
already at its end-of-turn value while the UI is still animating the first event.

### Battle UI: manager → handler → minion

Three tiers (documented on the wiki, see below):

1. **`BattleUIManager`** (`UI/Battle/`) — the only script that talks to game logic. Owns the event
   queue, a `Dictionary<string, UIShrimpState>` cache, and dispatch. Picks the **first** handler
   whose `CanHandle` returns true, so handler event sets must not overlap.
2. **Handlers** (`UI/Battle/BattleEventHandlers/`) — one per event *family*, all extending
   `BattleEventHandlerBase`. They orchestrate: read the event, decide what happens, tell minions.
   **They must never touch an `Image` or TMP field directly.** To add one: subclass, fill in
   `HandledTypes` and `Handle`, put it on a child object under `BattleUIManager`, and add it to
   the `handlerScripts` list.
3. **Minions** (`UI/Battle/MinionScripts/`) — do the actual visual work and know nothing about
   `BattleEvent`. `CommandBox` is a coordinator over `ICommandBoxPanel` implementations;
   `ShrimpInfoDisplay` ×2 sits behind `InfoDisplayGroup`, which routes an id to the right display.

The logic never sends a "battle started" event, so `BattleUIManager` raises a plain C# event,
`BattleInitialized`, at the end of `InitializeBattle`. `RosterHandler` listens for it and binds
both info displays to the starting shrimp. Without it the displays stay blank until the first
`SwitchingShrimp`.

**Where the battle UI lives.** The real UI is in two prefabs, `Assets/Prefabs/UI (Canvas).prefab`
(command box panels, info displays) and `Assets/Prefabs/BattleUIManager.prefab` (manager,
handlers, `BattleUIInput`). Right now only `UITestNoTouchie.unity` uses them. A prefab can't
reference objects in another prefab, so the handler→`CommandBox`/`InfoDisplayGroup` and
`BattleUIInput`→`CommandBox` refs are **scene overrides** and need re-wiring in any new scene.
Debug-only pieces (`BattleDebug` with `BattleUIDebugDriver` + fake `ShrimpState` teams,
`DebugCanvas` with `BattleDebugPanel`) are scene objects and must not go into the prefabs.

**Animation seam:** every minion mutator takes an `Action onComplete` and handlers wait via
`yield return WaitFor(done => display.SetHealth(hp, max, done))`. Today the callbacks fire
immediately. DOTween Pro is already a dependency — when animations land, the tween goes *inside*
the minion method and calls `onComplete` when it finishes, and no handler changes. Every spot is
marked `// TODO (animation):`.

### Input

**Never call `new GameControls()`.** The generated wrapper builds a fresh copy of the action asset
from embedded JSON every time, so multiple copies means rebinding one changes nothing anywhere
else — this is exactly why the old rebind screen silently did nothing.

`GameInput` (`UI/Input/`) holds the one shared instance and owns rebind persistence.
`GameInputBootstrap` is self-installing (`[RuntimeInitializeOnLoadMethod]`, nothing to place in a
scene) and repoints each scene's `InputSystemUIInputModule` at that shared asset, because the
EventSystem otherwise drives navigation from the project asset instead.

Rebinding uses a **pending-edit model**: opening the settings screen suspends the player's
overrides so the game runs on factory defaults, edits accumulate in `KeybindEditSession` without
going live, and they commit on exit (or factory-reset if two actions collide). That is deliberate
anti-softlock design — the settings screen must always stay navigable no matter what the player
has bound. Note the four Navigate actions each rebind **two** slots (`NavUp`-style *and* the
`UINavigation` composite part), since menus navigate off the composite and gameplay off the other.

The live actions asset is `Assets/Input/GameControls.inputactions` (map `Battle`).
`Assets/InputSystem_Actions.inputactions` is the untouched Unity template, referenced by nothing.

### Menus

Menu animation is **composition, not inheritance**. `MenuBase` (`UI/Menus/`) knows nothing about
how a menu animates: it collects `IMenuAnimation` components off itself and its children, plays
them all, and fires `onComplete` when the last one reports back. Same shape as `MenuInteractable`
collecting `IMenuFeedback[]`, just with completion callbacks since animations take time.

`MenuAnim_Transition` (`UI/Menus/MenuAnimationModules/`) is the workhorse module: a list of
targets plus separate opening/closing settings, each with independently toggleable **move / fade
/ scale** channels. Modules are grouped by *shared timing*, not by property — one module means
"these things animate together, like this". `stagger` is what the target list is for; the main
menu's four-button waterfall is one module with four targets and `stagger: 0.1`, and a negative
stagger runs the cascade backwards for the exit.

A new kind of animation is a new class implementing `IMenuAnimation` — no changes to `MenuBase`.
Subclass `MenuAnimationBase` to inherit the snapshot/restore bookkeeping (it caches each target's
position/scale/alpha on Awake and puts them back in `ResetState`, so a module cleans up after
itself). A menu with no modules falls back to a plain fade.

`MenuManager` drives transitions and calls the `OnMenuOpened`/`OnMenuClosed` hooks; `MenuBase`
also exposes matching `UnityEvent`s for inspector-wired responders. `SettingsMenu` uses those
hooks to start and commit the keybind session; `MainMenu` and `CreditsMenu` are deliberately
empty subclasses that exist only to hold the scene's script reference.

The three menus are **fully migrated** — 9 `MenuAnim_Transition` modules are wired in
`MainMenu.unity` (4 / 3 / 2) and confirmed working, so the old migration helper is gone. Don't
reintroduce animation data on `MenuBase`.

`MenuInteractable` + `IMenuFeedback` is the same composition pattern for button feedback — add
`UIFeedback_*` components alongside it rather than writing per-button behaviour.

### Assets

`ResourceManager.Get<T>(path)` is the only asset loader; it caches hits *and* misses, so a bad
path logs once rather than every frame. `UISprites` wraps it for UI art, prefixing
`BattleKeys.RootPaths.UI` and falling back to `test.placeholder`.

Data lives in ScriptableObjects under `Assets/Shrimp/{Shrimp,Moves,Abilities,Statuses}/`. These are
**not** under `Resources/`, so they can't be loaded by id — the UI reaches moves and statuses
through the `UIShrimpState` that already holds references to them.

- **Keybinding is code-complete**, and partly wired (last checked 2026-08-30): all 8 `KeybindRow`s
  have their action set and `KeybindEditSession` sits on `SettingsMenu`. Only `bindingText` is

  minion exists and is referenced, and a play-mode pass through every event type ran clean.
  Since the logic can't drive a battle yet, `BattleUIDebugDriver` auto-initializes a fake 3v3
  and `BattleDebugPanel` gives it a keyboard-navigable button grid. The panel also reselects a
  button whenever the selection falls off the screen.
- **`ShrimpState.instanceID` is still never assigned** (always null), so every event's `sourceId`
  is null and the UI can't tell shrimp apart. This blocks most of the battle UI and is Owen's to
  fix. The UI derives player/enemy by parsing the intended `shrimp.player.1` format
  (`BattleSideResolver`), since nothing else marks a side.
- Several reproducible crashes and a win/lose inversion exist in `UIAndLogicCommunicator/`.
  **Report them, don't fix them** — see the wiki page for the specifics.
